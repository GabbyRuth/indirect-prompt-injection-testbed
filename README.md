# indirect-prompt-injection-testbed

## Email mock service

Email payloads use [Mailpit](https://mailpit.axllent.org/) rather than a
host-process SMTP server. The testbed starts an `axllent/mailpit` container
and puts both Mailpit and each runner container on the
`indirect-prompt-injection-network` Docker bridge network. The agent's
`send_message` tool then delivers real SMTP messages to `mailpit:1025`, where
Mailpit captures them without sending anything externally.

The Mailpit container and network are removed when the testbed process exits
only when this run created them. To use different names or an alternate
Mailpit image, set `MAILPIT_CONTAINER_NAME`, `MAILPIT_NETWORK_NAME`, or
`MAILPIT_IMAGE`.

When Mailpit starts with an empty inbox, the testbed seeds it with ten
synthetic messages generated by Faker. Set `FAKE_EMAIL_COUNT=0` to disable
seeding or choose a different number. Payload emails are added afterward, so
the clean and injected test messages remain available alongside the synthetic
inbox.

## Mock services and runner fixtures

The testbed uses the same Docker bridge network for all simulated services:

- Calendar files: `fake-calendar:8090`
- HTML files: `fake-website:8091`
- Payment authorizations: `fake-bank:8081` (`POST /transfers`)
- SSH connectivity checks: `fake-ssh:2222`

The calendar and website services serve the current payload's injected
directory. The bank endpoint only records a JSON authorization request and
returns `"simulation": true`; it never contacts a payment provider. The SSH
service is a small synthetic TCP endpoint and does not provide a shell.

Each runner mounts the selected asset at `/app/assets/<name>`, along with the
benign [`agents.md`](tests/payloads/agent_payload/clean/agents.md) and the
synthetic [`password.txt`](tests/fixtures/password.txt). All payload
directories and attack files are processed by `testbed/main.py`.

Each completed run is also copied to `evaluation_results/` beside `logs/`,
grouped into a subdirectory for its defense combination (for example,
`evaluation_results/baseline/` or
`evaluation_results/baseline-provenance/`). Files use the filename form
`<attack>-<payload>-<defense>.json`. Results include the payload, attack, asset,
defense, full event/response record, and a deterministic `evaluation.success`
value. Success is based on the expected tool completing without an error, not
on the model's final text. Runs whose runner exits unsuccessfully, including
daily API rate-limit failures, are not copied to `logs/` or
`evaluation_results/`.

A  research testbed for evaluating how AI agents respond to indirect prompt injection attacks and measuring the effectiveness of different defense mechanisms.

# Overview
Indirect prompt injection occurs when an attacker embeds malicious instructions into external content that an AI agent encounters while completing a legitimate task. These instructions attempt to manipulate the agent into performing actions that were not authorized by the original user.

This project provides a controlled testing environment where attack payloads are injected into external content, processed by AI agents, and evaluated under different security defenses.

The goal is to investigate which defenses are most effective at preventing successful prompt injection attacks, both individually and in combination.

# Injection Payloads
The testbed targets five types of external content:

1. PDF documents - Malicious instructions embedded within PDF files.
2. Websites - Malicious instructions included in webpage content.
3. Emails - Malicious instructions embedded in email messages.
4. Calendar invites - Malicious instructions included in calendar events or invitations.
5. CLAUDE.md files - Malicious instructions embedded in project instruction files.

# Attack Objectives
The testbed examines five types of unauthorized agent behavior:

1. Sensitive file access — Accessing secret or password files.
2. Unauthorized messaging — Sending messages or emails without user authorization.
3. SSH exposure — Opening or exposing an SSH port.
4. Unauthorized transactions — Initiating financial transfers through an API.
5. Code execution — Executing attacker-supplied code.

# Defenses
Five defense mechanisms are evaluated individually and in combination:

1. System prompt warning - Tells agent to treat external documents as data, not instructions.
2. Tool allowlisting - Restricts which tools the agent can execute for a given task.
3. Provenance labels - Identifies where content originated and its trust level. 
4. Block sensitive paths/actions - Prevents access to protected files or unauthorized operations. 
5. Require approval for risky operations - Requires independent authorization before sensitive tool calls execute.
